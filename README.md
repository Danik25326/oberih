Мова програмування з вбудованою стійкістю до збоїв.  
Власний рантайм на Rust — один бінарний файл, нуль залежностей.

```oberih
resilient fn getOrder(id: String) -> String
    deadline(2s)
    retries(3)
    fallback(cachedOrder)
{
    let result = fetchOrder(id)?
    return result
}
```

## Встановлення

**Готові бінарники** (Linux, macOS, Windows) — на сторінці Releases репозиторію. Кожен архів
містить виконуваний файл, README і каталог `examples/`; поруч лежить файл `SHA256SUMS`.

```bash
# Linux/macOS: завантажте архів для своєї платформи, перевірте суму і розпакуйте
sha256sum -c SHA256SUMS --ignore-missing
tar xzf oberih-v0.3.0-linux-x86_64.tar.gz
./oberih-v0.3.0-linux-x86_64/oberih version
```

Збірки Linux: `linux-x86_64` (glibc, збудована на Ubuntu 22.04) і `linux-x86_64-musl` (повністю
статична; працює на будь-якому дистрибутиві, зокрема Alpine). Для macOS є `arm64` (Apple
Silicon) і `x86_64`; для Windows — `x86_64`. Збірки для Linux на arm64 поки немає.

**Docker** (не потребує нічого, крім Docker):

```bash
docker run --rm ghcr.io/<власник>/<репозиторій>:latest version

# запустити свій сервіс із поточної папки
docker run --rm -p 8080:8080 -v "$PWD":/app ghcr.io/<власник>/<репозиторій>:latest run app.obh

# або зібрати образ самому
docker build -t oberih .
docker run --rm oberih run /opt/oberih/examples/29_http_server.obh
```

Образ працює від імені звичайного користувача (не root) і використовує `tini`, тож
`docker stop` зупиняє контейнер одразу. `serve` без хоста слухає `0.0.0.0`, тож порт
доступний ззовні контейнера.

**Випуск нової версії** (для автора): піднімте `version` у `Cargo.toml`, зробіть
`git tag v0.3.1 && git push origin v0.3.1` — CI збере архіви для всіх платформ із
контрольними сумами, створить Release і опублікує образ.

## Що вміє мова

```oberih
// Resilience як синтаксис
resilient fn fetch(url: String) -> String
    deadline(2s)
    retries(3)
    fallback(cached)
{ ... }

// Result<T,E> і ? оператор
let data = fetch("url")?

// Struct з reference semantics
struct Point { x: Number, y: Number }
fn Point.distance(self: Point) -> Number { ... }

// Generics
struct Box<T> { value: T }

// Pattern matching
let msg = match result {
    Ok(v)  => "отримали: " + v,
    Err(e) => "помилка: " + e,
    _      => "невідомо"
}

// Гілка match (і гілка if-виразу) може бути блоком: виконуються ВСІ інструкції,
// значення — останній вираз (якщо його немає — Nil), а `return` виходить із функції.
let n = match fetch() {
    Ok(v)  => v,
    Err(e) => {
        println("помилка: " + e)
        return 1          // вихід із функції, а не значення гілки
    }
}

// Паралельне виконання
let h1 = spawn fetchA("url1")
let h2 = spawn fetchB("url2")
let r1 = h1.join()

// HTTP клієнт
let resp = httpGet("http://api.example.com/data")?
println(resp.body)

// Логічні оператори
let a = true && false   // false
let b = true || false   // true
let c = !true           // false

// Модульна система
import "lib/math.obh"
import "lib/strings.obh"

let result = add(10, 5)        // з math.obh
let s = capitalize("oberih")   // з strings.obh
let result = upgrade(weak)

// Вбудований тест-ранер
fn testAdd() -> Bool { return add(1, 2) == 3 }
```

## Map (словник)

```
let user = {"name": "Оксана", "age": 30}     // літерал; {} — порожній
user["city"] = "Київ"                         // індексація
user.age = user.age + 1                       // user.key == user["key"]
let n = user["нема"]                          // відсутній ключ -> nil
mapGet(user, "zip", "-")                      // значення за замовчуванням
for (k in user) { println(k, user[k]) }       // for перебирає ключі
```

- Ключі: `String`, `Number` або `Bool` (інші — помилка). Порядок вставки зберігається.
- Map — **посилальний тип** (як struct і list): `let b = a` не копіює, зміни бачать усі.
- Рівність `==` не залежить від порядку ключів.
- `mapMerge(a, b)` повертає **новий** Map; `mapSet`/`mapDelete` змінюють на місці — обидва амортизовано O(1).
- Типи: `Map<String, Number>` у параметрах/поверненні; typechecker перевіряє ключі й значення.
- `jsonParse` повертає `Map` для об'єктів, тож `resp.info.summary` працює як раніше.

## Лямбди й замикання

```
let double = fn(x) => x * 2                 // вираз-тіло
let clamp = fn(x: Number) -> Number {         // блок-тіло, з типами
    if (x < 0) { return 0 }
    return x
}
map(xs, fn(x) => x * 2)                       // функції вищого порядку приймають лямбди
```

- Захоплення — **за значенням** у момент створення лямбди; List/Map/struct — посилальні типи, тому зміни їхнього вмісту видно й через замикання.
- Типи функцій: `Fn` (будь-яка) або `Fn(Number, String) -> Bool` (конкретна сигнатура) — у параметрах і полях.
- Лямбди зберігаються між рядками REPL так само, як звичайні `let`.

## Регулярні вирази

Власний рушій (Pike VM) — час пошуку лінійний за розміром тексту й шаблону, тож
катастрофічний backtracking (ReDoS) неможливий, на відміну від naive backtracking-рушіїв.

```
let re = regex("(\\d+)-(\\d+)")?           // компіляція; Err при некоректному шаблоні
re.test(s)                                  // Bool
let m = re.find(s)                          // nil або {text, start, end, groups}
re.findAll(s)                               // List таких Map
re.replace(s, "$2-$1")   re.replaceAll(...)  // $1, $2 — посилання на групи; $$ — літеральний $
re.split(s)
```

Скорочення для одноразового використання: `reTest`, `reFind`, `reFindAll`, `reReplace`, `reReplaceAll`, `reSplit` (кожен викликом компілює шаблон заново — для циклів компілюйте через `regex()` один раз).

Підтримка: `. [] [^] \\d \\w \\s \\D \\W \\S \\b \\B ^ $ ( ) (?: ) | * + ? {n} {n,m}` (жадібні й ліниві `*? +? ??`), `(?i)` на початку шаблону. Без зворотних посилань, lookahead/lookbehind і іменованих груп.

## Пакетний менеджер

```
oberih init my-app                              # oberih.toml + src/main.obh
cd my-app
oberih add mathutils --path ../mathutils        # локальна залежність
oberih add web --git https://github.com/u/web.git --branch main
oberih run                                      # без аргументу — бере entry з oberih.toml
```

`oberih.toml`:
```toml
[package]
name    = "my-app"
version = "0.1.0"
entry   = "src/main.obh"

[dependencies]
mathutils = { path = "../mathutils" }
web       = { git = "https://github.com/u/web.git", branch = "main" }
```

- Це навмисно НЕ повний TOML — рядкова підмножина, якої досить для цієї схеми (секції, `ключ = "рядок"`, інлайн-таблиці `{ }`, коментарі `#`).
- `path`-залежність береться як є; `git` клонується (мілко, `--depth 1`) у `.oberih/deps/<ім'я>`. `tag`/`rev` фіксують версію назавжди (кеш більше не оновлюється); без них кожен запуск оновлює до останнього коміту гілки.
- У коді залежність використовується за іменем: `import "mathutils/utils.obh"` розв'язується відносно кореня залежності `mathutils`, а не поточного файлу.
- `run`/`check`/`test`/`explain` без аргументу файлу шукають `oberih.toml` вгору по директоріях (як `Cargo.toml`) і використовують `entry`.
- Реєстру пакетів немає — лише `path` і `git`. Версія на кшталт `mathutils = "1.0"` — явна помилка з поясненням, а не мовчазне ігнорування.

## REPL

```
>>> let x = 5
= 5
>>> if (x > 0) {
...   print("додатне")
... }
додатне
>>> :history
    1  let x = 5
    2  if (x > 0) {  ⏎ print("додатне")  ⏎ }
>>> !1
= 5
```

- **Багаторядковий ввід:** незакрита `(`, `[` чи `{` продовжує читання з підказкою `... `, доки дужки не збалансуються. Рахується на рівні токенів лексера, тож дужка всередині рядка чи коментаря не рахується.
- **Історія:** `:history` показує команди поточного й попередніх сеансів (зберігається у `~/.oberih_history`); `!N` повторює запис №N, `!!` — останній.
- Немає навігації стрілками вгору/вниз по історії під час набору — це вимагало б "сирого" режиму термінала і нової залежності (rustyline/crossterm), а REPL свідомо тримається нуля залежностей поза TLS.

## Асинхронність: кооперативний `spawn`

`spawn` — більше не окремий потік ОС, а легка **кооперативна задача** у
планувальнику VM (як у Node.js/asyncio: один потік, задачі перемикаються на
точках очікування):

```
fn worker(name: String, delay: Number) -> String {
    sleep(delay)                      // призупиняє ЦЮ задачу, не весь процес
    return name + " готово"
}
fn main() -> Number {
    let a = spawn worker("A", 300)
    let b = spawn worker("B", 100)
    println(a.join(), b.join())       // join призупиняє, поки задача не завершиться
    return 0
}
```

- Точки призупинення: `sleep(ms)`, `h.join()`, `h.join(секунди)` (таймаут → `Err("timeout")`),
  і **мережеві виклики** `httpGet`/`httpPost`/`httpPut`/`httpDelete`. `h.isDone()` не призупиняє.
- **Неблокуючий HTTP:** запит виконується у робочому потоці над простими рядками
  (`Value` потоки не перетинають), а задача-викликач призупиняється; решта працює,
  поки чекає мережа. 5 запитів по 0.5с — 504мс замість 2500мс. Одночасно не більше
  `MAX_IN_FLIGHT_IO` (256) запитів у потоках, решта — у черзі (тисячі задач із
  `httpGet` не створять тисячі потоків ОС). Помилка з'єднання — звичайний `Err(...)`.
- Перевірено: 3 задачі по 100–300мс — 0.31с загалом (послідовно 0.6с); 100 000
  одночасних сплячих задач — 0.77с; рекурсія 100 000 рівнів усередині задачі.
- Планувальник: черга готових задач + мін-купа таймерів + мапа очікувачів
  (без сканування всіх задач на кожен крок). Ліміт `MAX_TASKS` = 1 000 000
  (безкінечне створення задач — чиста помилка, не вичерпана пам'ять).
- Помилка всередині задачі не валить програму — її отримує `join` як `Err(...)`.
- Нескінченне взаємне очікування задач дає помилку «дедлок», а не зависання.
- Побічний ефект: збирач циклів більше не мусить боятись паралельної зміни
  даних — одночасно виконується лише одна задача.

**Чесні межі:**
- Це **не паралелізм**: усі задачі на одному ядрі. Для I/O-навантаження (мікросервіси,
  запити) це те, що треба; для паралельних CPU-обчислень — ні (старий `spawn` на
  потоках ОС таке вмів; свідомо проміняно на кооперативність).
- Читання/запис файлів (`readFile` та ін.) **усе ще блокують** весь планувальник
  на час виклику (мережа — ні, див. нижче).
- Призупинити можна лише на `sleep`/`join`/HTTP; довгий цикл без них не віддає
  керування іншим задачам (кооперативність, не витіснення).
- Неблокуючим є лише ПРЯМИЙ виклик `httpGet(...)`. Якщо передати його як значення
  (`map(urls, httpGet)`), виклик іде через блокуючий шлях функцій вищого порядку.
- `spawn` функції з модифікаторами стійкості (`deadline`/`retryBudget`/...)
  виконується синхронно, одразу (їхня логіка зав'язана на рекурсивний механізм,
  що не вміє призупинятись).
- У REPL кожен рядок — новий VM: хендл `spawn` не переживає рядок (дає зрозумілу
  помилку), задачі, не завершені до кінця рядка, відкидаються.
- Завершені задачі лишаються в пам'яті, доки живе VM (повільне зростання при
  мільйонах `spawn` без кінця роботи програми).

## Чому `Arc<Mutex<>>` ще на місці (виміряно, а не здогадка)

Планувалось прибрати `Mutex` після переходу на кооперативний `spawn`. Заміри:
цикл із 1 захопленням lock на ітерацію (індексація списку) лише на ~20–25%
повільніший за чисту арифметику без жодного lock; основна ціна — сама
диспетчеризація інструкцій (~17нс на інструкцію, у кілька разів повільніше
зрілих байткод-VM). Прибирання `Mutex` дало б максимум ~20% на коді, що
інтенсивно працює з колекціями, але:
- `Rc<RefCell<>>` робить `Value` не-`Send`, а на `Send` досі спираються мережеві
  робочі потоки (`http_client`/`http_server` передають лише прості рядки, але
  `IoDone`/`Incoming` йдуть каналом) і повернення результату з потоку з великим
  стеком (`run_with_big_stack`);
- кооперативний `deadline` УЖЕ зроблено (див. розділ нижче), тож головна перешкода
  прибрана; лишається переробити ці канали й `run_with_big_stack`.
Висновок: співвідношення виграш/ризик усе ще помірне — пріоритет: швидкість
доступу до полів struct і `Value`, і лише потім `Mutex`.

## Кооперативний `deadline` / `timeout`

Раніше КОЖЕН виклик функції з `deadline`/`timeout` породжував окремий потік ОС з
величезним стеком і **новою копією VM** (разом із клоном усього модуля). Прострочений
потік не можна було зупинити: він жив у фоні, їв процесор і міг далі робити побічні
ефекти (`httpPost`, запис у список), хоча викликач уже отримав `Err("timeout")`.

Тепер така функція — звичайна задача планувальника з дедлайном, у тій самій VM:

* **Нескінченний цикл чи затяжна рекурсія переривається:** час перевіряється раз на
  1024 зворотних переходи/виклики кадрів (дешево, без накладних витрат на кожну інструкцію).
* **`sleep`, `join`, мережа:** планувальник прокидається рівно о дедлайні й скасовує
  задачу, навіть якщо вона спала чи чекала відповіді.
* **Прострочена задача зупиняється повністю** — жодних зомбі-потоків і фонових побічних ефектів.
* **Вкладені виклики успадковують суворіший дедлайн:** внутрішня функція з `deadline(10s)`
  усередині зовнішньої з `deadline(200ms)` не проживе довше за 200 мс.
* Немає потоку й клону VM на виклик (швидше), а стан (circuit breaker, ліміти) тепер спільний.
* Рекурсія через resilient-функції обмежена `MAX_RESILIENT_DEPTH` (2 000 рівнів) —
  контрольована помилка замість вичерпання потоків.

**Чесні обмеження:** один виклик вбудованої функції не переривається (блокуюче читання
файлу, `sort` величезного списку) — дедлайн спрацює після його завершення; задачі, створені
`spawn` усередині функції, при її таймауті НЕ скасовуються; функції з `retries`/`fallback`/
`circuitBreaker` і далі виконуються рекурсивним шляхом (на що вказує `MAX_RESILIENT_DEPTH`).

## Безпека

**TLS-клієнт (`httpGet` та ін. по `https://`).** Використовується rustls зі стандартною повною
перевіркою: ланцюг сертифікатів до довіреного кореня, термін дії, відповідність імені хоста.
У коді немає ні опції, ні «небезпечного» режиму для вимкнення перевірки. Довірені корені —
вбудований набір `webpki-roots`; додаткові CA можна підключити змінною `SSL_CERT_FILE`
(корисно за корпоративними проксі з перехопленням TLS). CI на кожному запуску звертається до
`expired.badssl.com`, `wrong.host.badssl.com`, `self-signed.badssl.com` і
`untrusted-root.badssl.com` (`examples/31_tls_verify.obh`) і падає, якщо хоч один сертифікат
прийнято (мережевий збій чужої служби лише пропускає хост). Основний доказ не залежить від
мережі: Rust-тести `tls_*` у `src/http_client.rs` піднімають локальний TLS-сервер із власним CA
і перевіряють відхилення недовіреного видавця, простроченого сертифіката та чужого імені, а
також приймання довіреного (парний контроль).

**Обмеження HTTP-клієнта.** `timeout` (аргумент `httpGet` та ін., за замовчуванням 10 с) — це
ЗАГАЛЬНИЙ дедлайн на весь запит: підключення, TLS-рукостискання, запис і читання. Сервер, що
віддає дані по байту, не може затримати клієнта довше. Відповідь читається в пам'ять не більше
16 МіБ (`MAX_RESPONSE_BYTES`); більша дає `Err("… відповідь перевищує ліміт …")`. Відомі межі:
`timeout = 0` означає «без дедлайну» (ліміт розміру діє завжди); сам DNS-запит стандартна
бібліотека Rust обмежити таймаутом не дозволяє.

**Сервер (`serve`).** Ліміти на розмір заголовків і тіла, кількість з'єднань і час (див. розділ
про сервер), відхилення `Transfer-Encoding: chunked` і суперечливих `Content-Length`, очищення
CR/LF у заголовках відповіді, приховування деталей внутрішніх помилок. TLS на боці сервера
немає — ставте за reverse-proxy.

**Чого ще немає:** ліміту пам'яті процесу, обмеження частоти запитів (rate limiting) на
сервері, ізоляції недовіреного коду (мова виконує програму з повними правами процесу).

### Хеші, підписи, кодування (інтеграції без сторонніх бібліотек)

`sha256`, `hmacSha256`, `hmacSha256Hex`, `constantTimeEq`, `hexEncode/Decode`,
`base64[Url]Encode/Decode`, `base64[Url]EncodeHex/DecodeToHex` (міст для сирих байтів),
`uuid`, `randomHex`. Достатньо для перевірки підпису вебхука (Stripe/GitHub), JWT HS256 і
ланцюжків HMAC (AWS SigV4); приклад: `examples/33_webhook_jwt.obh`. SHA-256/HMAC реалізовано
в `src/stdlib_crypto.rs` без нових залежностей і перевірено векторами NIST FIPS 180-4 та
RFC 4231, а JWT збігається з токеном jwt.io; випадкові байти — з криптографічного
генератора ОС.

Чесні межі: це **не** криптографічна бібліотека загального призначення. Немає шифрування
(AES/ChaCha), асиметричних підписів (RSA/Ed25519, тож JWT RS256/ES256 не підтримується),
KDF (PBKDF2/Argon2/bcrypt): **паролі цими функціями зберігати не можна**. Підписи й токени
порівнюйте лише через `constantTimeEq`, не через `==`.

### Перевірка імен (`oberih check`, `run`, LSP)

Typechecker повідомляє про **невизначені** функції, змінні, конструктори struct і цілі
`spawn` (раніше такий код проходив «✓ типи коректні» й падав лише під час виконання), з
підказкою про опечатку: `Невизначена функція 'compte'. Можливо, ви мали на увазі 'compute'?`
Відомими вважаються: локальні змінні й параметри (у тому числі замикання та параметри `Fn`),
функції й struct/enum програми, вбудовані функції. Межі: імена **типів** в анотаціях
(`a: Nope`) і невідомі **методи** (`p.nothere()`) поки не перевіряються; LSP аналізує один
файл, тому для документа з `import` перевірку імен вимикає (імпортованих імен він не знає).
Файли в `examples/sketches/` — ескізи дизайну з неіснуючими об'єктами, вони цю перевірку
не проходять і не запускаються.

### Language server (`oberih lsp`) і розширення VS Code

`oberih lsp` — LSP через stdin/stdout (`Content-Length`), без залежностей. Підтримується:
діагностика (лексер, парсер, typechecker; точні діапазони, колонки в UTF-16), форматування
документа (те саме, що `oberih fmt`), структура документа, перехід до визначення, hover із
сигнатурою, автодоповнення (ключові слова, типи, модифікатори, вбудовані функції, імена з
файлу, поля структур після `.`). Автодоповнення працює і на синтаксично некоректному коді
(стійкий скан токенів), бо під час набору документ майже завжди «зламаний».

Межі: аналіз одного файлу (`import` не розгортається); немає rename, references,
signatureHelp, семантичних токенів; автодоповнення після `.` не залежить від типу виразу
ліворуч. Клієнти — довільний редактор із LSP або `editor/vscode-oberih` (збірка й
встановлення: `editor/vscode-oberih/README.md`; налаштування `oberih.serverPath`).
Сервер не падає від довільного вводу: розмір повідомлення й заголовка обмежені, кожне
повідомлення обробляється під `catch_unwind`, позиції клієнта безпечно обрізаються; це
перевіряють юніт-тести, фазинг протоколу й `tests/lsp_e2e.rs` (справжній бінарник, коди
виходу за специфікацією: `shutdown`+`exit` → 0, інакше 1).

### Soak-тест: тривале навантаження й витоки пам'яті

`bench/soak/soak.py` запускає `bench/soak/server.obh` і дає змішане навантаження (алокації,
JSON, тіла до 1 МіБ, помилки обробника, `resilient fn`, логи, метрики) плюс «ворожих» клієнтів
(обірвані заголовки, сміття, завеликі заголовки й тіла, обірване тіло, chunked). Знімає RSS,
потоки, дескриптори, `gcStats`, запити в обробці й латентність, а наприкінці перевіряє:
нахил RSS після прогріву, повернення потоків/дескрипторів до початкових значень, ріст
GC-об'єктів на запит, p99 «початок/кінець», відсутність неочікуваних відповідей, живість
сервера протягом усього прогону та коректну зупинку за SIGTERM.

```
cargo build --release
python3 bench/soak/soak.py --duration 300                      # типовий прогін
python3 bench/soak/soak.py --scenario known --duration 120     # відомі межі (цикли, spawn): лише звіт
python3 bench/soak/soak.py --scenario leak-selftest            # самоперевірка: течу МАЄ бути виявлено
python3 bench/soak/soak.py --only /work --duration 60          # діагностика одного маршруту
```

Лише стандартна бібліотека Python; потоки й дескриптори міряються на Linux (на macOS лише
RSS), Windows не підтримується. Пороги залежать від тривалості: короткий прогін (< 30 хв)
ловить грубі витоки (від ≈ 1 КБ на запит), довгий (за замовчуванням ≤ 5 МіБ/год) повільні, бо
«сходинки» алокатора на великих тілах запитів з часом згасають. CI: `.github/workflows/soak.yml`
(швидкий прогін на кожен push/PR; довгий, 5 год, щонеділі та за запитом). Ліміт одного job на
hosted-runner — 6 год; для 24-годинного прогону потрібен self-hosted runner.

**Що знайшов soak-тест.** Реєстр збирача циклів тримав `Weak` на кожен створений список/Map/
struct і чистився лише в `gcCollectCycles`, тож будь-яка довготривала програма росла
пропорційно ЗАГАЛЬНІЙ кількості створених об'єктів (≈ 14 КБ на запит у `/work`, ≈ 0,6 КБ у
`/health`). Тепер реєстр самоочищується (амортизовано O(1) на об'єкт) і обмежений кількістю
живих об'єктів; тести `registry_stays_bounded_when_objects_die` і
`pruning_keeps_live_objects_and_cycles_collectable`.

### Фазинг і межі вхідних даних

Усе, що приймає дані ззовні, перевіряється фазером (`src/fuzz_tests.rs`, працює на stable, без
залежностей): лексер, парсер, typechecker, компілятор, форматер (результат має знову
парситись і бути ідемпотентним), JSON, regex, розбір HTTP-запиту сервера (результат не має
залежати від розбиття на мережеві шматки), розбір відповіді клієнта, `oberih.toml`, формат
рядків логу. Кожен збій автоматично зменшується до мінімального відтворювача. Швидкий
прогін є в кожному `cargo test`; нічний (`.github/workflows/fuzz.yml`) — у сотні разів більший,
із новим зерном щоночі. Власний прогін: `OBERIH_FUZZ_SEED=… OBERIH_FUZZ_ITERS=200000 cargo test --release fuzz_`.
Це НЕ coverage-guided фазинг (libFuzzer/AFL): він не бачить покриття коду.

Властивості, що перевіряються для коду: відсутність паніки/зависання; результат `fmt` знову
парситься, ідемпотентний і **не змінює значень літералів**; результат розбору запиту не залежить
від розбиття на шматки; JSON зберігається при `stringify → parse`. Крах процесу (SIGSEGV,
переповнення стека) не лишає мінімізованого файлу, тому перед кожним випадком вхід можна
писати на диск: `OBERIH_FUZZ_TRACE=/tmp/last cargo test --release fuzz_language` (файл
`/tmp/last.<тест>` після краху і є відтворювач); нічний прогін робить це сам.

Нічний прогін (`.github/workflows/fuzz.yml`) при збої пише підсумок у Summary й створює issue
з міткою `fuzz-finding` (якщо відкрите вже є, додає коментар). Знайдені відтворювачі зберігаються
як регресійні тести в `fuzz_regressions_from_nightly_runs` (`src/fuzz_tests.rs`).

Що це означає для мови:
- **Глибина вкладення коду** обмежена (`MAX_AST_DEPTH` = 2000 рівнів, сумарно дужки/блоки/типи
  та довжина ланцюжків `a + b + …`); глибше — звичайна помилка, а не аварія. Весь фронтенд
  працює у потоці зі стеком 64 МіБ; тест гарантує, що на максимально дозволеній глибині
  вистачає стеку навіть у 8 разів меншого.
- **JSON:** вкладення до 512 рівнів (`MAX_JSON_DEPTH`); число поза діапазоном f64 (`1e404`)
  — помилка, а не `inf`; `jsonStringify` ніколи не друкує невалідне `inf`/`NaN` (дає `null`).
- **`oberih.toml`:** ім'я залежності — лише літери/цифри/`_`/`-`/`.` (до 64 символів, без
  `..` і роздільників шляху), бо воно стає назвою теки в `.oberih/deps/`; значення git
  (`git`, `branch`, `tag`, `rev`) не можуть починатись з `-`. Виклики `git` ставлять `--`
  перед позиційними аргументами.

## Спостережуваність: логи й метрики

**Структуровані логи.** `logInfo("замовлення створено", {"id": 42, "user": "ann"})` — один рядок на
подію, у stdout (twelve-factor). Поза терміналом (контейнер, CI) це JSON, який збирають Loki,
ELK, CloudWatch:

```
{"ts":"2026-10-31T14:05:00.123Z","level":"info","msg":"замовлення створено","id":42,"user":"ann"}
```

У терміналі — читабельний текст: `2026-10-31T14:05:00.123Z INFO  замовлення створено id=42 user=ann`.
Функції: `logDebug`, `logInfo`, `logWarn`, `logError` і `log(рівень, повідомлення[, поля])`.
Налаштування: `OBERIH_LOG_FORMAT=json|text`, `OBERIH_LOG_LEVEL=debug|info|warn|error`
(за замовчуванням info). Значення з переводом рядка екрануються (захист від підробки логу),
зарезервовані імена `ts`, `level`, `msg` не перезаписуються (поле отримує префікс `field_`).
Повідомлення самого рантайму (старт сервера, сигнали, помилки обробників) ідуть тим самим
каналом, тож в агрегаторі це один потік подій.

**Access-лог сервера** (рядок на запит: `method`, `path`, `status`, `duration_ms`, `remote`)
вмикається `OBERIH_ACCESS_LOG=1`. У лог потрапляє лише шлях без параметрів запиту (вони можуть
містити секрети).

**Метрики Prometheus.** `metrics()` повертає текст у форматі Prometheus; віддайте його з будь-якого
маршруту: `return Response(200, metrics(), {"Content-Type": "text/plain; version=0.0.4"})`.
Сервер рахує сам: `oberih_http_requests_total{method,status}`, гістограму
`oberih_http_request_duration_seconds`, `oberih_http_in_flight_requests`,
`oberih_http_rejected_total{status}` (запити, відхилені ще до обробника: 400/413/431/503/504),
`oberih_uptime_seconds`, `oberih_build_info`. Свої лічильники: `metricInc("jobs_done")`,
`metricAdd("bytes", 512)`. Кардинальність обмежено навмисно: мітки лише `method` (невідомі методи
зводяться до `OTHER`) і `status`, шлях у мітки не потрапляє, власних лічильників до 1000.

**Чого ще немає:** трейсингу (ключове слово `traced` сьогодні лише записує прапорець у
компіляторі й нічого не робить у рантаймі), gauge/гістограм користувацьких метрик, експорту в
OpenTelemetry. Це чесна межа цієї версії.

## HTTP-сервер: `serve` і `stopServer`

```
struct Request {                 // поля заповнює сервер — оголосіть struct з такими полями
    method: String,  path: String,
    query: Map<String, String>,  headers: Map<String, String>,
    body: String,  remote: String
}
struct Response {
    status: Number,  body: String,  headers: Map<String, String>
}

fn handle(req: Request) -> Response {
    if (req.path == "/health") {
        return Response(200, "ok", {})
    }
    return Response(200, "привіт, " + req.query["name"], {"Content-Type": "text/plain"})
}

fn main() -> Number {
    let r = serve(8080, handle)   // блокує задачу до stopServer(); Err(текст), якщо порт зайнятий
    return 0
}
```

> Увага: тип `Map` без параметрів типізатор наразі сприймає як struct з іменем `Map`.
> Пишіть `Map<String, String>` (як вище) або повертайте struct.

* Кожен запит виконується в **окремій кооперативній задачі**: обробник може `sleep`, `httpGet`
  тощо, не блокуючи інші запити (це той самий планувальник, що й для `spawn`).
* Обробник отримує `Request` із полями `method`, `path`, `query` (Map), `headers` (Map, імена
  малими літерами), `body`, `remote`. Повертає `String` (200), Map/struct з `status`
  (за замовчуванням 200), `body`, `headers`, або `nil` (204). Помилка в обробнику -> 500;
  деталі пишуться лише в stderr, клієнтові не розкриваються.
* `serve(port, handler, host)` — третій аргумент необов'язковий (за замовчуванням `0.0.0.0`).
* `stopServer()` припиняє приймати з'єднання; `serve` повертає `Ok(nil)`, коли завершаться
  запити, що вже обробляються.
* **Graceful shutdown за сигналом.** Після виклику `serve` процес перехоплює SIGTERM і SIGINT
  (Unix) та Ctrl+C/Ctrl+Break (Windows): сервер перестає приймати нові з'єднання, **дочікується
  запитів, що вже виконуються**, і `serve` повертає керування — тож `docker stop` і оновлення
  без простою не обривають користувачів на півслові. Якщо запит не вкладається в час (за
  замовчуванням 20 с, змінюється змінною `OBERIH_SHUTDOWN_GRACE_SECS`), його обривають із
  відповіддю 503. Повторний сигнал — негайний вихід (код 130). Щоб Kubernetes/Docker встигли,
  їхній `terminationGracePeriodSeconds`/`--time` має бути більшим за цей час. Обробник сигналів
  встановлюється лише разом із `serve`: звичайні скрипти зберігають стандартну поведінку Ctrl+C.
* **Ліміти (захист від зловживань):** заголовки до 16 КБ і 100 штук, тіло до 1 МБ, до 512
  одночасних з'єднань (решта отримує 503), таймаути на читання/запис (15 с), на отримання
  заголовків (10 с) і всього запиту (30 с), на відповідь обробника (60 с -> 504).
  Відхиляються `Transfer-Encoding: chunked` (501), суперечливі `Content-Length` (400);
  значення заголовків відповіді очищаються від CR/LF.
* **Чесні обмеження цієї версії:** одне з'єднання = один запит (`Connection: close`, без
  keep-alive); тіло запиту/відповіді — лише текст UTF-8; немає TLS на боці сервера (ставте
  за reverse-proxy: nginx, Caddy, хмарний балансувальник); кожне з'єднання обслуговує окремий
  потік ОС (до 512).
  Задачі, створені `spawn` усередині обробника, після завершення не звільняються
  (повільне зростання пам'яті, якщо робити `spawn` на кожен запит): виміряно ≈ 126 байт
  на запит. Цикли посилань (`a` ↔ `b`) теж не збираються автоматично: ≈ 700 байт і 2 живі
  об'єкти на кожен цикл (див. розділ про збирач циклів і `gcCollectCycles`).
* Повний приклад із клієнтами в тому ж процесі: `examples/29_http_server.obh`.

## Замір швидкості: Perf

Окремі запуски бенчмарка на спільних CI-раннерах мають розкид до 2×, тому швидкість
оцінюють лише порівнянням двох збірок у ОДНОМУ завданні: **Actions → Perf → Run workflow**

### Профіль: де саме йде час (Profile)

**Actions → Profile → Run workflow** запускає VM під `valgrind --tool=callgrind` на Linux-раннері й
показує рядки коду `src/vm/mod.rs` із найбільшою кількістю виконаних інструкцій процесора
(таблиця в Summary, повний звіт — артефакт `callgrind-report`). Це детермінований підрахунок,
а не вибірка, тому результат не залежить від шуму спільного раннера і не потребує профайлера
на машині розробника. Поле `bench`: `loop` (арифметика) або `calls` (виклики функцій).

**Виміряний результат порівняння з оригіналом (Perf, 7 чергованих запусків, Ubuntu):**
арифметика −17%, `fib(27)` −29%, виклик функції −26%, метод struct −32%, виклик вбудованої
−30%, рядки без змін. Чиста арифметика досі ~9 нс на інструкцію — резерв лежить у самому
циклі виконання, і Profile призначений, щоб знайти його за цифрами, а не навмання.

## Оптимізація диспетчеризації: що зроблено (заміри — за вами)

Причини повільного циклу інструкцій знайдено читанням коду; зміни нижче
логічно безпечні, але **їхній ефект у цифрах ще не виміряно** — для цього є
`bench/bench.obh` (запуск: `cargo build --release && ./target/release/oberih run bench/bench.obh`).

- **Пошук функції за ім'ям — O(1).** `Module::find_fn_index` використовує
  хеш-підказку (`fn_hint`) замість лінійного `iter().position(..)`. Підказка
  перевіряється при кожному влучанні, а при промаху пошук падає назад на
  лінійний — тож функції, додані в `module.functions` напряму (REPL), знаходяться.
- **`Instr::CallGlobal { name, argc }`** замінює `LoadGlobal + Call` для викликів
  за ім'ям: без проміжного `Value::Fn(String)`, без повторного пошуку функції,
  без `format!("__builtin_..")` для вбудованих. Користувацька функція, як і раніше,
  має пріоритет над вбудованою; `sleep` лишається призупиненням задачі.
  Відмінність: виклик невідомого імені тепер повідомляє про помилку ПІСЛЯ
  обчислення аргументів (раніше — до).
- **Виклик методу struct**: ім'я `Type.method` збирається без `format!`, функція
  шукається один раз, приймач і аргументи переміщуються (раніше клонувались
  завжди, навіть коли користувацького методу не було).
- **Аргументи виклику**: `take_args!` (один `split_off`) замість n×`pop` + `reverse`;
  для простої користувацької функції аргументи переносяться зі стека прямо в
  локальні змінні нового кадру однією алокацією.

Не зроблено (кандидати, залежно від профілю): `Value::Str(String)` → `Arc<str>`
(107 місць у 8 файлах), зменшення розміру `Value` (зараз ~56 байтів через
`EnumVal(String, String)` та `Closure(String, Vec<Value>)`), доступ до полів
struct через `Mutex<HashMap<String, Value>>` (lock + хеш + клон на кожне читання).

## Явний стек викликів: глибока рекурсія обмежена пам'яттю, не стеком ОС

Раніше `fn sum(n) { return n + sum(n-1) }` обвалював ВЕСЬ процес (`stack
overflow`, SIGABRT) вже на ~2500 рівнях рекурсії — типового стека головного
потоку (8 МБ) на це не вистачало, бо кожен виклик Oberih-функції був ще
одним рекурсивним викликом Rust.

Це перший крок до продакшн-готовності (фундамент для асинхронності — щоб
колись призупинити виконання на `await`, потрібен стек, яким можна керувати
явно, а не рекурсія Rust):

- **Звичайні виклики** (без `deadline`/`retryBudget`/`circuitBreaker`/...) —
  включно з прямою й взаємною рекурсією, і виклики методів struct — тепер
  ідуть через явний стек кадрів (`Vec`, росте в купі), а не рекурсію Rust.
  Межа — `MAX_EXPLICIT_CALL_DEPTH` (500 000), і це справді пам'ять, а не
  стек ОС: 400 000 рівнів прямої рекурсії працюють за ~0.3с (швидше, ніж
  100 000 рівнів працювали старим шляхом).
- **Функції з модифікаторами стійкості** й далі йдуть старим, рекурсивним
  шляхом (`MAX_CALL_DEPTH`, 150 000) — їхня retry/circuit-breaker/timeout
  логіка зав'язана на рекурсивні виклики й окремі потоки; переписувати це
  зараз — окремий, значно ризикованіший крок.
- Код виконується на окремому потоці з 512 МБ стека (`run`, `test`, REPL).
- Понад межу — звичайна `RuntimeError` (Result, можна зловити), не крах;
  процес після такої помилки працює далі нормально.

**Побічні знахідки, виправлені під час цієї роботи:**
- `spawn` і функції з `timeout`/`deadline` колись створювали внутрішній потік ОС з
  малим (~2 МБ) стеком, тож глибока рекурсія всередині падала раніше, ніж на
  головному потоці. Тепер `spawn` — кооперативна задача, а `timeout`/`deadline` —
  теж (див. «Кооперативний deadline»), тож цієї проблеми й проблеми вичерпання
  потоків більше немає.

## Бітові оператори

```
6 & 3        // 2   AND
6 | 1        // 7   OR
6 ^ 5        // 3   XOR
~5           // -6  NOT (двійкове доповнення)
1 << 8       // 256 зсув вліво
256 >> 4     // 16  зсув вправо
```

- Операнди — цілі `Number` у межах ±2^53 (межа точного представлення f64); дробові чи виходять за межу — помилка виконання, а не мовчазне усічення.
- **Пріоритет — як у Python, не як у C**: `| ^ &` тісніші за порівняння, але слабші за зсуви. `1 | 2 == 3` означає `(1 | 2) == 3`. Зсуви `<<`/`>>` слабші за `+ -`, тож `2 << 1 + 1` це `2 << (1 + 1)`.
- `>>` навмисно не окремий токен лексера — інакше зламалось би закриття вкладених дженериків (`Map<String, List<Number>>` закінчується двома символами `>`). Парсер розпізнає дві сусідні `>` як зсув лише на рівні виразів, де дженериків немає.

## Збирач циклів посилань

Reference counting (у списках/Map/struct) не звільняє цикли:
```
let a = {"val": 1}
let b = {"val": 2}
a["next"] = b
b["prev"] = a
// a, b більше нізвідки не досяжні, але тримають одне одного —
// звичайний refcounting НІКОЛИ їх не звільнить.
```
- У **REPL** цикли розриваються автоматично після кожного рядка (корені — всі змінні сесії), і їх показує `:gc`.
- У коді — явно, вбудованою функцією: `gcCollectCycles(живе1, живе2, ...)` — усе передане лишається живим, решта зареєстрованого й недосяжного звідси звільняється. `gcStats()` повертає `{allocs, drops, live}`.
- Реєстр об'єктів і `gcStats()` — **локальні для потоку** (VM виконується на одному потоці): збирач одного потоку ніколи не чіпає об'єкти іншого. (Раніше реєстр був глобальним, і CI на Linux/Windows виявив, що паралельні потоки/тести ламали один одного.) Мережеві робочі потоки та потоки з'єднань сервера не створюють об'єктів мови (лише прості рядки).
- REPL виконує ВСІ рядки на одному постійному потоці-виконавці (інакше реєстр втрачався б між рядками).
- Друк (`println`, `:vars`) і `jsonStringify` структур з **циклами** безпечні: повторний вхід у вже відкритий контейнер дає `<цикл>` (у JSON — `null`) замість нескінченної рекурсії й краху.
- Обмеження: збирач не бачить локальних змінних, що живуть у стеках викликів (включно зі ще не завершеними задачами `spawn`) — у `gcCollectCycles(...)` передавайте явно все, що програма ще використовує. Паралельної зміни даних більше немає (задачі кооперативні, одночасно виконується одна), тож небезпека лише в забутих коренях.

## Відомі обмеження

- **Часові пояси:** тільки фіксовані зсуви від UTC у хвилинах (`isoTime(t, 180)`), без бази iana/tzdata. Іменовані пояси (`Europe/Kyiv` з переходом на літній час) не підтримуються — це вимагало б окремої залежності з базою даних поясів; робити її "приблизно правильною" самотужки гірше, ніж чесно її не мати.
- **Регулярні вирази:** без зворотних посилань (`\\1`), lookahead/lookbehind і іменованих груп — рушій свідомо обмежений до конструкцій, що гарантують лінійний час.
- **Вивід контейнерів:** рядки в списках/Map беруться в лапки (`["a", 1]`), але немає керування форматом (ширина, кастомний Display для struct).
