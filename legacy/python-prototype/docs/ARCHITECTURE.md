# Архітектура Oberih (план реалізації)

Цей документ описує технічний план побудови мови — від першого прототипу до
незалежного інтерпретатора. Заповнюється поступово, у міру просування.

## Загальний конвеєр виконання

```
myfile.obh (текст)
      ↓
   Лексер          — розбиває текст на токени (ключові слова, дужки, числа, ідентифікатори)
      ↓
   Парсер          — будує AST (дерево розбору) за граматикою мови
      ↓
   Type Checker     — перевіряє типи, Result<T,E>, Option<T>, вимогу deadline на корені
      ↓
   Tree-walking     — виконує AST напряму (Фаза 1)
   Interpreter        або
   Bytecode Compiler — генерує байткод + Stack VM виконує його (Фаза 2)
```

## Фаза 1: Tree-walking Interpreter

**Мета:** найшвидший шлях до працюючого прототипу, повністю незалежного від
інших мов (жодної транспіляції).

**Компоненти (плановані файли):**

```
oberih/
├── lexer.py           # текст → токени
├── parser.py          # токени → AST (за граматикою grammar.lark)
├── grammar.lark        # формальний опис синтаксису Oberih
├── ast_nodes.py        # класи для вузлів дерева (FunctionDecl, RetryModifier, ...)
├── typechecker.py      # перевірка типів + вимога deadline/retryBudget на корені
├── interpreter.py      # виконання AST: обробка resilient fn, Shared Budget, Result<T,E>
├── runtime/
│   ├── budget.py        # реалізація Shared Budget (deadline + retryBudget контекст)
│   ├── circuit_breaker.py
│   └── result.py        # Result<T,E>, Option<T> як рантайм-типи
├── cli.py              # команда `oberih run myfile.obh`
└── tests/
```

**Ключовий технічний виклик Фази 1:** реалізація Shared Budget — потрібен
механізм неявної передачі контексту (deadline, залишок retryBudget) через усі
вкладені виклики resilient-функцій, без явного прокидання параметра руками.
Найпростіший підхід на старті — контекстна змінна на кшталт thread-local /
contextvars (у Python це `contextvars.ContextVar`), яка автоматично
успадковується дочірніми викликами в межах одного асинхронного контексту.

## Фаза 2: Bytecode VM

Коли Tree-walking Interpreter працює і семантика мови обкатана на реальних
прикладах — компілюємо AST у власний байткод (стекова машина, у дусі ранньої
Lua/Python) для продуктивності. Ця фаза починається лише після того, як Фаза 1
демонструє коректну поведінку на всіх трьох еталонних сценаріях з `examples/`.

## Наступні конкретні кроки

1. Написати `grammar.lark` — формальну граматику для синтаксису з прикладів
   у `examples/`.
2. Перевірити граматику на всіх трьох `.obh` файлах — чи парситься без помилок.
3. Реалізувати мінімальний `interpreter.py`, що виконує програму без
   модифікаторів стійкості (звичайні функції, `let`, `return`).
4. Додати `retries` + `timeout` як перші модифікатори.
5. Додати Shared Budget (`deadline` + `retryBudget`) — ключова фіча.
6. Додати `fallback` + `ResilienceExhausted`.
7. Додати `circuitBreaker`, `idempotent`, `cache`.
